# 案例分析题：改进 “EduPro” 校园数字平台的敏捷交付流程

（2025 南京大学）

### 一、案例背景

#### 1 平台与组织概况

| 项目要素           | 说明                                                         |
| ------------------ | ------------------------------------------------------------ |
| **产品定位**       | “EduPro” 是⼀个面向师生的一站式 Web / 移动门户，集成课表、作业、科研仪器预约、校园卡充值、AI 问答等服务。目标用户 4 .1 万（教职工 0.5万 + 学生 3.6万）。 |
| **投资与里程碑**   | 预算 1780 万元（软硬件及运维三年）。 · T0 = 18 个月前：项目立项。 · T0 + 10 个月：MVP v0.1 内测。 · T0 + 14 个月：MVP v0.2 上线（当前版本）。 |
| **团队结构**       | ‑ **产品线 A/教学**、**B/科研**、**C/生活** 各 1 支 Scrum Team，共 15 人：  · PO × 1（兼管三队）  · Scrum Master × 1（兼任敏捷教练）  · Developers × 13（前端 5、后端 6、QA 2） |
| **现行流程**       | 采用 *Scrum + XP + CI/CD*： • 2 周 Sprint • 统一主干开发 • GitHub Actions 自动单元测试 + 容器打包 + 手动部署至云主机 |
| **关键利益相关者** | ‑ 校信息化中心主任（Sponsor） ‑ 教务处、科研院、后勤处（业务代表） ‑ 学生会 & 教师发展中心（用户代表） |

#### 2 典型 Sprint（最近一轮）快照

| 指标                     | 目标           | 实际             | 备注                           |
| ------------------------ | -------------- | ---------------- | ------------------------------ |
| Sprint Commit 完成率     | ≥ 80 %         | **30 %**         | 4 个高优 Story 被移至下 Sprint |
| 缺陷密度（上线后一周）   | ≤ 0.5 / KLOC   | **1.3**          | 高并发下卡片充值失败           |
| 主干构建成功率           | ≥ 95 %         | **71 %**         | 14 天内 25 次失败              |
| 平均恢复时间 MTTR        | < 1 h          | **6 h 15 min**   | 依赖回滚、数据库迁移冲突       |
| 部署频次                 | 每 2 周 ≥ 1 次 | **40 天仅 1 次** | 手动审批 + 业务窗口限制        |
| 用户净推荐值 NPS（β 版） | ≥ +25          | **‑4**           | 主要抱怨加载慢、登录偶发失效   |

#### 3 关键痛点与现象

1. 需求与 Sprint 目标失配
   - 缺少分级需求管理，Stakeholder 经常在 Sprint 中追加“紧急卡片”。
   - PO 独自维护 Backlog，未与团队共同估算 → 复杂度偏差大。
2. XP 实践流于形式
   - 结对编程只在代码评审时象征性进行。
   - TDD 覆盖率 25 %，远低于 DoD 75% 要求。
3. CI/CD 走样
   - Pipeline 步骤：`lint → 单测 → 构建 → 推镜像`，缺少自动化部署与回滚。
   - 构建失败后通常由单一 Dev 修复，平均 6 小时才恢复。
4. 看板失控，流动受阻
   - 看板“进行中”列常年 25 + 条目。
   - 无 WIP Limit，导致多任务并行、上下文切换频繁。
5. 缺乏可观测性与反馈闭环
   - 生产仅采集 CPU / 内存监控，无业务日志聚合。
   - 用户反馈渠道分散（企微群、公众号、小程序留言），缺乏统一登记与优先级评估。

#### 4 历史事件年表（节选）

| 日期       | 事件                                | 影响                                          |
| ---------- | ----------------------------------- | --------------------------------------------- |
| T0 + 9 月  | 首次集成测试，Bug > 300 条          | 决定“先上线 MVP 再优化”                       |
| T0 + 12 月 | 期末周高峰，登录服务雪崩            | 临时禁用单点登录，将 SSO 相关 User Story 降级 |
| T0 + 14 月 | v0.2 上线 3 天即回滚                | 数据库迁移脚本遗漏；CI 只跑单测未涵盖迁移验证 |
| T0 + 15 月 | 信息化中心对外承诺“暑假前上线 v1.0” | 给团队设定 3 个月硬 Dead‑line                 |

#### 5 组织文化与约束

- **交付压力**：校领导层强调“关键功能优先”，对技术债重视不足。
- **合规要求**：校园数据必须部署在教育网云区；安全扫描合格方可发布。
- **人力限制**：Scrum Master 同时承担 IT 审计任务，难以全时辅导团队。

| 任务                                              | 关键要点                                                     | 参考附件提示                  |

| **3. 重新设计 CI/CD 流水线的关键步骤与质量门禁**  | 覆盖：触发频次、自动构建‑测试‑部署、失败恢复策略             | Martin Fowler CI 核心实践列表 |

### 三、提交要求

**分析报告**（3000–5000 字）  ，针对 6 条分析任务：

- 结构：问题诊断 → 改进策略 → 实施计划 → 度量与风险
- 每条结论需附相应幻灯片页码/段落引用（可以引入幻灯片中没有涵盖的行业最佳实践，给出参考文献或链接）。
