# 5 持续集成

## 5.1 引言

### 5.1.1 持续集成（CI）的定义

**定义**：团队成员频繁（通常每天至少一次）将代码更改集成到共享代码库主线的软件开发实践 

**目的**：尽早发现并解决集成问题，降低复杂性和风险，避免“集成地狱” 

**核心机制**：每次集成触发自动化构建（编译、链接、自动化测试）

### 5.1.2 CI 的起源与动机

传统集成的痛点：

- 集成周期长，导致开发者与主代码库长时间不同步
- 最终集成时面临复杂的代码合并和难以发现的错误
- 微妙的语义错误难以调试，只在集成后环境中暴露
- 开发者在代码逻辑与解决冲突间频繁切换上下文，影响效率和积极性
- 害怕集成而避免必要的重构，导致技术债累积和代码质量下降
- 代码库逐渐“腐烂”，难以维护和修改

CI 的解决方案：

- 核心理念：通过非常频繁的集成（每天多次）消除传统集成的痛苦
- 效果：个体开发者偏离主线时间短，代码量小，降低合并冲突和复杂度
- 快速反馈：自动化构建和测试能快速发现问题，易于定位和修复
- 鼓励主线开发（Trunk-Based Development）



## 5.2 CI 实践示例：一个典型的开发集成流程

**步骤 1：获取最新代码**

- 从中央代码仓库拉取最新的主线代码，确保本地与主线同步
- 目的是基于最新代码开发，减少后续冲突

**步骤 2：本地构建与开发**

- 在本地运行完整的自动化构建脚本（编译、自动化测试）
- 确保开始更改前本地构建成功（“绿色”）
- 开发过程中可频繁运行本地测试

**步骤 3：集成前检查**

- 本地代码更改完成且测试通过后，再次从中央仓库拉取最新主线代码
- 合并最新更改到本地工作副本
- 再次在本地运行完整的自动化构建，确保与同事的最新更改和谐共存

**步骤 4：本地构建通过与推送**

- 若合并主线最新更改后本地构建仍成功，则可推送更改到中央仓库主线
- 推送操作通常会触发中央 CI 服务器自动执行一次集成构建，提供更权威的验证



## 5.3 持续集成的核心实践概览

### 5.3.1 维护单一的代码库主线（版本控制）

**核心原则**：所有项目所需纳入版本控制系统（VCS），维护单一共享主线。版本控制是持续集成的基石，支持协同、追踪历史。目前最流行的版本控制系统是 Git

**版本控制的内容**：源代码、测试代码、数据库模式及迁移脚本、配置文件、构建脚本、安装部署脚本、第三方库依赖定义，甚至工具链定义（如 Dockerfile）。目标是克隆仓库后即可构建、测试、运行整个产品

**处理依赖与构建产物**：

- **依赖**：大型二进制文件（编译器、库）可通过链接指向资产库，由构建脚本按需下载特定版本，避免“最新版本”引用
- **构建产物**：不应存入版本控制，应可随时通过自动化构建重新生成

**主线（Mainline） 的重要性**：代表项目当前、已集成的、准备部署的状态（Git 中通常是 `main` 或 `master`）。所有成员工作集成于此

**文本格式优先**：VCS 处理文本文件效果最好（易于 diff），优先选择文本表示形式（XML, JSON, YAML 等）

### 5.3.2 自动化构建

**必要性**：转化源码为可运行系统可能复杂（编译、打包等），**任何重复任务都应自动化**，避免手动操作的耗时和错误。目标是“一键构建”

**构建工具与脚本**：如 make, Ant, Maven, Gradle, npm scripts 等，脚本本身也需版本控制。**单一命令原则**：任何人检出代码后，通过单一命令即可完成构建

**构建脚本的依赖管理**：现代构建工具基于依赖网络，任务间声明依赖，仅当依赖项变化或目标产物不存在时才执行，提高效率

### 5.3.3 让构建自测试

**超越编译**：编译通过不等于程序正确，需自动验证代码行为

**自动化测试的角色**：全面的自动化测试套件作为构建的一部分运行，是 CI 中防止错误的主要手段。这种构建称为“自测试构建”

**Xunit 框架与测试文化**：JUnit, NUnit 等框架推动了单元测试和 TDD，催生“保持构建常绿”等术语

**自测试的目标**：所有测试通过（构建“绿色”）时，团队有信心产品无重大错误。好的测试套件应能捕获常见错误和破坏性修改

**超越单元测试的验证**：集成 Linter、代码格式化检查、静态分析工具、安全扫描工具、覆盖率检查等，提供更全面的代码质量保障

**不完美但有价值的测试**：即使不能捕获所有错误，频繁运行的、能发现部分问题的测试也极具价值，关键是持续投入和改进

### 5.3.4 每个人每天都向主线提交

**沟通本质**：集成是沟通活动，让团队快速响应变化

**频率要求**：“持续”意味着高频率，每个成员每天至少向主线提交一次

**日常集成循环**：更新 -> 开发 -> 本地构建/测试 -> 再次更新与合并 -> 再次本地构建/测试 -> 提交与推送

**快速发现与解决冲突**：

- **源代码冲突**：VCS 通常能检测

- **语义冲突**：代码语法无冲突但逻辑不兼容（如函数签名或行为变更） 

- 频繁集成使变更集小，易于定位和修复问题

**语义冲突与自测试的重要性**：VCS 无法检测语义冲突，自测试构建是关键武器。良好的测试套件应覆盖主要行为路径，暴露语义冲突

### 5.3.5 每次主线提交都应触发构建

**必要性**：不能完全依赖开发者自觉在推送前进行本地构建，因纪律松懈或环境差异可能引入错误

**自动化保障**：需 CI 服务在一致、独立环境中自动执行完整集成构建（编译、测试）

**持续集成服务（CI Service）**：如 Jenkins, GitLab CI, GitHub Actions 等，监控仓库、检出代码、执行构建、记录日志、报告结果、通知团队

**立即修复失败的构建**：保持主线构建健康是团队最高优先级，构建失败需立即停下其他工作修复

**如何修复失败的构建**：首选**恢复（Revert）**导致失败的提交，让主线快速回到健康状态。开发者本地修复后再尝试集成

### 5.3.6 保持构建快速

**重要性**：CI 核心价值在于快速反馈，构建过长会降低效果，打断心流，增加修复成本

**目标时间**：主提交构建（Commit Build）经验法则是十分钟内完成

应对慢速测试：构建流水线（Deployment Pipeline）

- 主要瓶颈：通常是慢速的集成测试或端到端测试
- 解决方案：将构建分解为多阶段，第一阶段（提交阶段）快速反馈，后续阶段运行更全面但慢的测试

流水线：提交阶段（Commit Stage）

- 目标：十分钟内为提交提供反馈
- 内容：编译代码、快速单元测试（可能用测试替身）、快速静态分析
- 反馈：失败则立即通知并优先修复，通过才进入下一阶段。

流水线：后续阶段与优化

- 内容：集成测试、端到端测试、性能测试、安全扫描等
- 处理失败：也需尽快修复，但可能不像提交阶段失败那样“停止一切”
- 优化：并行化、分布式构建、定期审视测试策略

### 5.3.7 隐藏未完成的工作

- **挑战**：CI 要求频繁集成未完成功能，如何确保主线始终可部署/可发布而不受影响。
- 技术：团队采用多种技术来管理主线上的未完成功能：
  - **特征开关/特征标志（Feature Toggles）**：通过配置动态启用/禁用功能，最常用灵活
  - **按抽象分支（Branch by Abstraction）**：引入抽象层使新旧实现并存，逐步切换
  - **黑启动/暗启动（Dark Launching）**：部署到生产但不暴露给用户，内部监控测试

**（隐含） 让获取最新可执行文件更容易**

**（隐含） 让每个人都能看到构建状态**

## 5.4 持续集成的好处

**降低风险**

- **减少集成风险**：小规模集成易于解决合并冲突
- **快速发现错误**：自动化构建和测在几分钟内发现问题，修复成本低
- **更容易定位错误**：小变更集快速缩小问题范围
- **减少“集成地狱”**：集成成为日常而非令人生畏的里程碑

**促进改进与发布**

- **鼓励并支持重构**：自动化测试作为安全网，使开发者更有信心重构
- **提高代码质量**：自动化测试和静态分析持续运行，提升整体质量。
- **更频繁、更可靠的发布**：主线代码接近可发布状态，发布成为低风险事件
- **发布成为业务决策**：技术障碍移除后，发布由业务需求驱动



## 5.5 CI 与相关概念及实践

**CI 与特性分支（Feature Branching）**

- 严格来说，CI 与长期特性分支互斥；CI 核心是持续集成到主线
- 短暂（不超过一天）的特性分支与 CI 兼容，前提是频繁合并回主线并验证

**CI 与持续交付（Continuous Delivery, CD）**

- 关系：CD 是 CI 的自然延伸。CI 是 CD 的必要前提
- CI 关注点：代码频繁集成到主线并通过自动化构建和测试验证，确保主线健康、可工作
- CD 目标：确保通过 CI 验证的主线代码，能通过自动化步骤使任何版本都可被部署到生产，发布成为低风险、按需活动

**持续部署（Continuous Deployment）**
定义：CD 的更进一步，通过所有验证的主线构建会自动部署到生产，无需人工干预

**CI 与拉取请求（Pull Requests） 及代码评审**

- 挑战：PR（尤其需要前置评审时）可能延迟集成，打破快速反馈循环
- CI 团队实践：结对编程、集成后评审、分类处理、优化评审流程

**CI 与数据库管理**

- 挑战：数据库模式变更和测试数据管理
- 解决方案：进化式数据库设计
  - 版本化迁移脚本（如 Flyway, Liquibase）与代码一同版本控制
  - 自动化迁移集成到构建和部署流程，确保代码与数据库结构同步
